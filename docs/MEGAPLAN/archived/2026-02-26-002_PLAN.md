- Config provider: solo parametri e provenance.
- Nessuna dipendenza diretta GUI -> Engine interno specifico.
- Nessuna dipendenza diretta GUI -> file storage.
- Nessuna dipendenza diretta Engine -> widget/UI.
- Nessun parametro normativo hardcoded.
- Trace sempre presente nei risultati.

Se un modulo viola i confini:

- blocca l’avanzamento,
- rifattorizza subito verso interfaccia/adapter,
- aggiorna i documenti di architettura e deprecazione.

**4) Obiettivo “primo risultato operativo”**

Arrivare a una Alpha con:

- Avvio applicazione stabile.
- Launcher GUI usabile.
- Almeno un flusso completo Input -> Calcolo -> Risultato -> Persistenza -> Report.
- Modulo incendio separato e non accoppiato al core strutturale.
- Test mirati verdi per ogni stream.
- Regressione globale accettabile secondo policy blocker.

Definizione di operativo:

- utente apre progetto,
- imposta input,
- avvia calcolo,
- vede risultato tracciato,
- salva e ricarica progetto,
- ottiene output standard,
- il log mostra passo-passo cosa il software ha fatto e come ha interpretato input e parametri.

**5) Sistema di debug log estremamente approfondito (obbligatorio)**

Implementare un sistema di osservabilità cross-modulo con requisiti minimi:

Copertura:

- ogni modulo,
- ogni GUI/page/dialog,
- ogni azione utente,
- ogni comando software,
- ogni passaggio di orchestrazione,
- ogni calcolo,
- ogni lettura/scrittura storage,
- ogni caricamento configurazione,
- ogni plugin load/unload,
- ogni warning/error/fallback.

Eventi minimi tracciati:

- correlation_id per sessione e run_id per esecuzione,
- user_action (click/comando/modifica input),
- input_received e input_normalized,
- config_resolved con provenance,
- engine_started/finished,
- repository_read/write,
- output_generated,
- validation_passed/failed,
- plugin_compatible/incompatible,
- fallback_applied,
- exception_captured con contesto.

Qualità log:

- timestamp ad alta risoluzione,
- livello severità,
- modulo sorgente,
- entità coinvolte,
- durata operazione,
- esito.
- Niente dati sensibili non necessari.

Output log:

- console sviluppo + file persistente per progetto/run.
- Se possibile, viewer log in GUI.
- Ricerca e filtraggio per modulo, run_id, severità.

Obiettivo esplicito:

- in ogni istante sia possibile sapere cosa il software sta eseguendo e come sta interpretando l’input.
